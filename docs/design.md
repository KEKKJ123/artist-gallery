# 画师图库 设计文档 v0.10（2026-10-28）

> 本版按红豆 03:53～04:00 确认的简化流程取代 v0.9 的组共享 tag／页码必填方案，见 [ADR 0010](decisions/0010-图片直接属性与原名增量导入.md)。旧开发库处理以 [ADR 0009](decisions/0009-开发期旧库不迁移.md) 为准；历史 ADR 不改写。
> 当前交付 T1：新建库、原名复制导入、外部目录增量去重、来源建议与两区只读浏览。检查、属性编辑、正常／强制归档和撤销仍待 T2／T3；不要把目标写成已实现功能。

## 1. 优先原则与范围

- **开发第一目标：减少用户无用或繁琐操作，即使代码需要多做工作。** 可靠信息预填、人只核对纠错，不让技术容器或冗余弹窗变为整理门槛。
- 本地图片优先：一图一卡，图片直接关联内容 tag、画师、多个平台来源；不同文件可作为版本。不要求建立作品组或隐式单图组。
- 保留 `character:红豆`、`series:明日方舟` 等内容分类，未来可扩展；初版不先做庞大词库、继承引擎或复杂标签规则。
- 设计规模 1 万张图片以内；重复／相似图是需要处理的情况，不把每次普通导入都变为人工查重任务。
- Windows、Android（目标 APK／Termux 开发路径）与局域网；离线手动功能完整，不依赖平台接口。下载器与相似算法后置。

## 2. 图片直接属性

```text
图片 42（内部稳定 ID）
├─ 内容 tag：character:红豆、series:明日方舟
├─ 画师：某画师 → Pixiv 用户 ID、X uid／handle、其他账号
├─ 来源：Pixiv 作品 123456789 → pn=2（可空）、发布时间（可空）
├─ 来源：X 帖子 1849000000000000000 → pn=0（可空）、发布时间（可空）
└─ 文件版本：具体文件、原名、hash、尺寸、相对路径
```

- 图片自身 ID 唯一定位本地图片；Pixiv 作品／X 帖子 ID 定位平台发布，可能包含多张图。按发布 ID 检索不要求 pn；精确到帖内位置时才用 pn。
- pn 是从 0 起的对应发布位置，不是总页数，不是独立 tag，也不承担本地图片身份。不同平台分别记录，未知不填 p0。
- 图片的作品／帖子 ID 与画师的用户／账号 ID 不混淆。画师资料集中维护，图片直接引用；发布者尤其转载账号不自动等于创作者。
- 初版一图可关联一个已知画师，未知允许空；合作创作的多作者扩展后续按使用反馈评审，不提前造分组继承。一个画师多图、多平台账号。
- 内容 tag 直接挂图片，可一图多 tag。多选批量添加分别作用于选中的每张图，无分组步骤，不影响未选图。
- 平台来源以标签式体验显示和搜索，但内部为平台帖子与图片关联，不是把 ID、pn、角色、画师统统塞进无类型字符串。
- 同平台不同发布可以并存，跨平台不重复卡片；初版同图同帖保存一个可空 pn，同帖出现多次同图的位置表达暂不做。
- 发布时间属于对应平台发布，不是导入时间或文件修改时间；手填／附带可靠资料可补，允许未知，不能承诺离线解析链接就得出作者与时间。
- “图在 X 发布过”不等于“本地文件从 X 获得”或“这是原图”。线索、人工判断与文件获取证据分开。

## 3. 实际结构（新格式基线 5）

以 `schema.sql` 与后续 `db.MIGRATIONS` 为准。本轮可替换初始 schema，旧格式没有迁移桥。

| 表 | 职责与主要约束 |
|---|---|
| `image` | 稳定 ID、`state=inbox/archived`、画师外键、入库时间；不存唯一组或通用页码 |
| `image_file` | 图片的实际文件版本，hash 唯一、相对路径不区分大小写唯一；原名、尺寸、missing；每图最多一个展示版本 |
| `artist/account` | 画师名／备注及多平台账号，uid 与 handle 分开，数字 ID 存文本 |
| `tag/image_tag` | 命名空间与名称、直接图片关联；不建 work／group／共享 tag 继承表 |
| `post` | 平台＋发布 ID 唯一、可空发布时间 |
| `image_source` | 图片与帖子、可空 pn、pending／confirmed／rejected、确认时间；同图同帖唯一 |
| `source_evidence` | 输入原文、文件关联、规则指纹、置信度、平台／ID／pn；输入＋规则去重，保留矛盾依据 |
| `import_record` | 每次正式批次的文件编号、输入原名与时间；不覆盖首次原名 |
| `op_log` | 导入与删源审计；后续归档／属性编辑再交付各自撤销 |

- 导入事务成对创建图片与展示文件，不会让来源／tag join 产生重复卡片。列表先按图片分页，再批量附加关系，避免 N+1 查询。
- 不同字节暂作独立图片＋文件，T1 不实现版本合并或优选；表情／服装差分不能吞成低画质版本。
- 后续扩展结构正常版本升级，不能反复要求丢库。application_id=`0x41475259`，user_version 从 5 起，旧程序最多支持 4，避免误开新库。
- 打开先只读识别，旧 v1～v4／未知／损坏／过新库写入前报错；不静默清空或重建。`init` 只接受新目录或空目录，遇既有文件不覆盖。旧库由红豆手动处理，AI 不动真实图库。

## 4. 原名存储与文件安全

```text
图库根目录/
├─ library.db
├─ images/
│  ├─ _inbox/123456789_p0.png
│  └─ archived/原来的中文标题.jpg
└─ .cache/thumbs/   可重建，按内容 hash 缓存
```

- 合法原名和扩展名大小写尽量保留；同名不同内容追加 `_2` 等后缀，不覆盖。非法字符／Windows 保留名／超长名称只必要清理，完整原名另存，仍可在资源管理器浏览。
- hash 与内部图片／文件编号另存，不强制写入文件名；修改角色、画师或平台来源不重命名／搬文件。
- 归档状态是数据库明确值，不能从文件夹、是否有 ID 或是否有分组推断。T2 在两区移动时实现校验、日志、恢复与撤销；T1 没有归档写入口。
- 所有文件路径相对图库根目录，统一 `/`；整体复制到手机仍可识别。
- 导入只复制。独占创建目标、校验和落盘后才允许确认删源；竞争者占用目标不覆盖，失败保留源文件。图库内部移动也须复制→校验→删除旧副本。
- 删除外部源文件须显式确认（ADR 0005），逐一复核库记录、实际副本和源内容；重复输入、失败与预演不进删除清单。先提交 `delete_source` 的 pending 意图，提交失败不删；删除前再校验，删除后更新 deleted／failed 结果。中断或结果写入失败保留 pending、明确提示人工核对，`status` 显示数量；不把 pending 当成未删除，不自动重试。
- 文件被外部移动后的 hash 找回、missing 扫描保留为后续能力，T1 不实现；损坏／缺失的重复命中明确报告异常，不静默覆盖。

## 5. 外部目录增量导入

用户再次选择外部源目录即可增量导入，不必新建同步任务：

| 输入变化 | 行为 |
|---|---|
| 字节相同、原名相同 | 检查图库副本；复用身份与存储，原整理结果不变 |
| 字节相同、改名／换目录 | 同上，记录新名称并提取不重复的新来源线索 |
| 新增不同文件 | 新图进收件箱，自动建议待审 |
| 源目录减少 | 不联动删除图库副本或分类 |
| 同名文件内容改变 | 新文件另存并加防重名后缀，不继承旧分类 |
| 命中已有 hash 但副本缺失／不一致 | 报错保留输入，不声称安全完成，不自动修复 |

- 不是镜像、后台监控或双向同步；直接在图库 `images/` 增减不属于外部增量入口。
- SHA-256 只判断字节相同；改内部元数据、压缩或转格式可能变 hash，不能凭视觉相似自动继承分类。
- hash 相同不重置归档状态、画师、tag 或人工来源；仍提取新名称的建议。每次正式输入可追溯，相同输入／规则不无限增加重复建议。
- 预演只读，不改库、不复制、不迁移、不同步规则。扫描隐藏目录跳过，直接指定的隐藏文件仍可处理。
- 视频／GIF 同样识别与入收件箱，不做专用缩略图或原图优选，视频不读宽高。

## 6. 建议、核查与归档（T1 仅前半段）

```text
安全入库 → 来源建议 → 人工核对／多行链接补充 → 保存
                                               ↓ 用户明确选择
                                      正常归档／强制归档／稍后
```

- 高／中置信一律仅建议；保留 Pixiv、X、Zerochan 的已校准规则。`_pN` 可预填 pn，单独 ID／无页码链接不推定 p0。规则命中不是已确认来源。
- `image_source` 是一条来源关联的当前属性；证据保留每次输入和规则。新线索可并存但不覆盖已确认或已驳回的结果，冲突后续核查界面处理。
- 收件箱保留全部／有建议／无建议和整体计数，服务端筛选。建议来自未核查来源证据；已确认／已驳回来源的证据不再显示为待审建议。
- T2 检查默认单张前进，可随时多选；不因保存下一张而归档。**一行一个链接的多行文本框，只追加**；已有来源单独列出，删除需明确操作，清草稿不删来源。
- 逐行解析，坏行不阻塞好行；同图同平台同 ID 去重。多选含义是“全部链接添加给每张所选图”，明确确认范围，不按行分配、不传播到未选图。
- **正常归档只要求至少一条人工确认的具体平台发布；pn、发布时间、画师、内容 tag 不强制齐全。** 额外待核查来源不阻断。无来源可显式强制归档，不伪造字段或核查状态，也不跳过文件安全。
- 缺项混合批次先报告，由用户另选正常／强制范围，不自动部分执行或暗中分流。
- 已归档可继续补资料，不因新建议自动退回。归档／编辑须按 ADR 0007 的影响范围与已实现撤销决定确认；多选来源范围确认独立保留。

## 7. 浏览与后续功能

- 主导航只有收件箱／已归档，不按平台拆目录；图片 ID、角色、画师、平台来源可组合检索，搜索 UI 后续交付。
- T1 `/api/inbox?filter=`、`/api/archived`、`/api/navigation`、`/api/platforms`；旧 `/api/folder(s)` 删除，旧 `?folder=` 明示失效回收件箱，不改释为来源条件。
- 一图一卡固定一行标题：已确认来源 ID 优先、否则疑似 ID、否则原名。紧凑标题取稳定首条匹配，详情展示全部建议／来源，不因此指定主来源。完整原名保留 title。
- 图片详情投影含直接角色 tag、画师、多来源及其 pn／时间；T1 能读取和展示结构中已有资料，但没有对应编辑入口，不宣称已交付打 tag 功能。
- 文件大小、tag 补全／最近使用／默认角色、画师绑定、多行链接与归档编辑后续交付。角色默认值不自动猜文件内容；别名词库与通用复杂规则不先做。
- 平台规则包最小仅平台定义、链接模板及文件名／URL 规则，官方与自定义统一格式另审；画师规则和角色词库不强绑，不执行任意脚本。
- 原文件追溯未排期：找最接近画师发布原文件的版本，非最大文件／PNG 排行榜。哈希粗筛、内容比对和来源证据只辅助，不自动删除差分，允许未知；不阻塞初版。

## 8. 技术栈、安全与实施顺序

- 保留 Python 3.12+、SQLite、Pillow、Starlette／uvicorn、Vue／Pinia／Vite；无新运行依赖，composables／store／core 分层不倒流，异步防竞态。
- Android APK 为 Briefcase／Chaquopy＋WebView 目标；运行依赖纯 Python 或 Chaquopy 有包，Photo Picker／SAF 等存储方向沿 ADR 0004，M4 前验证文件选择。
- 默认 localhost，显式 LAN 模式无登录保护；资源本地打包。GPL-2.0-or-later，M1 完成后公开。
- 不开 WAL；复制备份前停写／停服务，Git 不备份图库。双端不能同时改，导出恢复与双端合并后续评审。
- T0 已完成路线说明；**T1 本 PR：新格式、导入、增量、建议、两区基础浏览**。T2 检查／多行链接／归档与撤销，T3 直接内容 tag／画师编辑与检索，T4 平台包。不再开发组共享 tag 或旧库映射。
- 暂停分支 `feat/image-details-captions` 保留，不整批合并；固定标题按新模型实现，文件大小后续适配复用。
- 实施验收与剩余设计项见 [transition.md](transition.md)，现有模块见 [modules.md](modules.md)，交互见 [frontend-style.md](frontend-style.md)。
