# 0008 以图片为中心：分组、来源、版本与归档状态分别建模

- 日期：2026-10-28
- 状态：路线已采纳，分阶段实现；本记录不代表数据库或运行程序已切换。
- 需求：[design.md](../design.md) v0.9；过渡与验收：[transition.md](../transition.md)。

## 背景

旧实现把平台帖子作为作品组的建立依据，图片仅属于一个组，文件按平台重命名和存放；收件箱用 `work_id IS NULL` 判断，文件夹视图再按路径统计已归档。完全相同的文件在识别新来源前被跳过。

这使平台来源近似变成互斥归属，也把平台帖、用户组织的作品组、具体画面和磁盘文件混在一起：
- 同图跨 Pixiv／X 发布时可能产生不同组，重复导入又可能丢掉新增来源；
- 部分重叠的帖子无法表达用户保留两个组、且共用一张图片；
- 组内顺序和各平台帖内位置无法共用一个页码；
- 自动识别成功不等于人工核查，更不等于用户已经决定归档。

红豆于 2026-10-28 重新确认了围绕图片、组共享 tag、多平台来源、人工检查与强制归档的工作流程。

## 决定

1. **一图一卡**。图片代表具体画面，文件是它的版本；同图多来源／多版本不复制网格卡片。相似但不同字节的文件未确认前保守保留，内容差分是独立图片。
2. **图片与组多对多**。组内顺序属于成员关系；跨平台帖子重叠不自动合组，由用户选择保留两组或合成。
3. **组共享内容 tag**。图片汇总所有所属组的有效 tag 并保留来历；移出组只解除该组带来的关联，不抹掉别组仍提供的 tag。
4. **平台发布与组分开**。图片分别关联发布记录及平台页码；来源标签可像 tag 一样展示／筛选，但不是整组共享的普通 tag。发帖者不自动等于画师，发布关联不自动证明本地文件的获取来源或原图身份。
5. **识别只生成待审查线索**。文件名自动填平台、帖子 ID 和平台页码；检查页逐图核查，多行框一行一链接、只追加来源。多选表示全部链接加到每张所选图，必须明确确认范围；不按行分图，未知平台位置不填 p0。规则更新不能覆盖人工确认。
6. **归档与核查独立**。归档显式记录为收件箱／已归档。至少一条人工确认的具体发布与平台页码满足正常归档来源条件；额外未核查来源不阻断。来源不足可由用户强制归档，保留未知与未核查状态；“强制”不越过文件安全。混合缺项批次先报告，由用户另选，不自动部分执行或分流。
7. **目标存储两区且中性命名**。收件箱／已归档，不再按平台目录决定图片身份；标签、画师、组、来源的变化不触发文件搬动。原文件名独立保留。关系迁移先保留旧路径，物理搬库另做预览、确认、校验与恢复。
8. **平台规则包保持最小范围**。官方／自定义规则统一格式是目标；不强绑画师库或 tag 词库，不造任意脚本规则引擎，公开稳定 API 另行评估。
9. **原文件追溯后置**。优先识别接近画师发布原文件的版本，不按大小／格式自动选优；相似算法辅助候选、关系由人工确认，不作为基本整理前置条件。

## 理由与代价

- 图片不因平台或收藏方式不同而重复；多组 tag、平台位置和文件版本各有可解释的归属。
- 自动化负责提取，人只核对和纠错；不要求算法猜出画师、跨平台同图或原文件真伪。
- 显式强制归档给资料不全的图片保留出口，不把未核查信息伪装成已确认。
- 代价是关系数增加，旧 `image.work_id/page`、`source.work_id` 和路径统计不能继续作为长期真相；需追加迁移，适配读写、查询去重与日志。
- 旧库无法证明哪些记录经过人审；必须保留历史依据、单独评审映射，不以自动确认掩盖信息缺失。不能恢复旧程序跳过重复导入时未保存的线索。
- 文件名不再能恢复全部关系，备份与恢复更重要；数据库升级与文件搬迁应分离，代码回滚不等于数据库降级。

## 实施与待定

保留仓库和已合入的基础模块，不重开项目、不改写 main。先合设计，再分别交付关系迁移、最小核查归档闭环、多组 tag／画师与浏览、规则包和存储迁移。

暂停分支 `feat/image-details-captions` 不合并、不改写；固定标题和文件大小日后按模块适配复用，不带入旧来源模型和综合资料包方案。

具体 SQL、旧自动归档状态映射、旧来源到具体图片的核查映射、作者编辑层级、组外单图操作、草稿／队列与中性文件命名均未在本 ADR 定死。相关实施前按 [transition.md](../transition.md) 的评审点确认，不把助手建议当作用户已确认需求。
