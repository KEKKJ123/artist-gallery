## 1. 范围与交付规则

1. 沿用代码仓库、模块化成果和 Git 历史，不重开项目、不改写 main。
2. 红豆已确认旧开发图库有异地备份，可自行手动清理；**不开发旧库数据迁移、字段／状态／来源映射、旧日志转换或平台目录搬迁**。
3. 旧库由红豆处理，AI 不删除、清空或重建。新程序应拒绝旧格式，提示在新目录建库、重新导入；当前运行代码尚未实现这一拒绝边界。
4. `feat/image-details-captions` 继续暂停，不合并、不改写或删除。选择性复用界面与测试，不继承旧来源查询和综合资料包假设。
5. 各阶段从最新 main 开分支，经 PR 由红豆审核合并。阶段可拆多个完整、可验证的 PR；不长期维护两套生产业务，也不能先破坏入口再承诺下次修复。
6. 本 PR 仍只改文档与约定，不改 schema、版本管理、Python／Vue 或静态产物，不打开用户图库。
7. 放弃旧库兼容是一次开发期决定；新格式之后仍有版本管理、备份与升级机制，代码回滚不等于数据库能降级。

## 3. T1：新建图库基线与配套读写

### 3.1 模型能力（具体 SQL 待评审）

- 逻辑图片／文件版本分开；图片有独立稳定身份，具体文件有 hash、相对路径与原文件名记录。
- 图片／作品组多对多，顺序属于成员关系；内容 tag 组共享，搜索汇总且保留组来源。
- 平台帖子独立于组；图片／帖子关联有平台页码、核查状态与依据，不能复用组页码。
- 整理状态明确持久化，独立于路径、组和来源；至少一条完整确认来源满足正常归档，强制归档不伪造确认。
- 规则线索与人工确认分开，重复输入不覆盖已确认结果；相同文件的新来源不丢，不同字节保守保留。
- 作者不能直接从发帖账号推定；画师编辑层级、合作署名及冲突处理、单图使用组共享 tag 的入口仍需明确，但不再有旧记录映射待定项。

### 3.2 格式识别与拒绝旧库

1. 新格式须能与旧 v1～v4 可靠区分；格式标识和版本号在 T1 评审，不重用旧版本值造成歧义。
2. 打开入口先做格式检查，旧库在任何升级、平台同步或其他写入前被拒绝。错误说明旧开发库不受支持，提示在新目录建库与重新导入，不自动清空或尝试转换。
3. `init` 不覆盖已有数据库／冲突文件；无效、过新、未知、损坏库不能被当作“没库”重建。
4. 旧库测试使用合成 fixture，比较拒绝前后数据库字节和媒体文件不变，不操作用户旧库。保留损坏／权限／过新等错误处理回归。
5. 可替换当前初始 schema、移除只服务旧模型的运行时迁移链和兼容代码；历史留在 Git。新格式之后仍追加可验证的升级，不能每次更新要求丢库。
6. 修改 schema、格式标识与版本管理前先与 sky 协调，防止并行冲突。

### 3.3 交付完整性

- 新建库、导入、查询、CLI 和前端基础浏览成套适配；不保留旧写入器写出新模型不完整数据。
- T1 配套最小新导入／状态查询，新写入路径不得继续绑定平台。T2 在可运行基础上丰富检查与归档，而不是等 T2 才修 T1 的断链入口。
- 不实现旧路径兼容、不搬旧文件、不转换旧日志。重新导入备份／原文件只执行普通安全导入并生成新建议，不恢复旧数据库关系。
- 临时 API 投影仅用于同一新模型的前端过渡，需说明退出节点；不得借此保留旧单组字段作为另一份真相。

## 4. T2：最小核查与归档闭环

在 T1 的新建库与基本读写上，分批实现：

1. 文件名建议、收件箱整体计数与有无建议筛选，安全导入报告区分文件新增、存储复用和线索新增。
2. 检查默认单张前进、随时多选；多行链接逐行解析、只追加，已有来源明确解除。
3. 多选追加是“每个有效链接 × 每张所选图”，执行前明确确认范围；无页码不填 p0，不因批量追加自动确认。
4. 对应平台位置与具体帖子人工确认；至少一条完整确认可正常归档，额外待核查来源不阻断。
5. 正常／强制归档范围明确，缺项整批先报告、用户另选，不部分执行；归档及其撤销同时交付。
6. 复用固定标题与文件大小，绑定逻辑图片当前展示的文件版本，不照搬旧首条来源／通用页码语义。

保存核查与“下一张”不隐式归档，追加来源和组编辑不自动改变整理状态。

## 5. T3／T4 与存储

- T3：多组成员编辑、共享 tag 来历、画师绑定与多平台账号、关系浏览搜索；计数／分页去重，组修改展示全部影响。
- T4：最小平台规则包的格式、版本、优先级、校验与官方／自定义统一；画师规则另行设计，不做任意脚本引擎。
- 目标两区为收件箱／已归档；**新写入路径在 T1 就确定，不推迟到 T4，不再开发旧平台目录搬家工具**。最终文件命名与分片实施前评审。
- T2 归档如需在两区移动新文件，须实现复制校验、日志、失败与中断恢复；这属于新模型正常操作，不是被取消的旧库搬迁。SQLite 事务不能代替文件恢复。
- 文件 hash 扫描找回与 missing 仍保留为新文件版本的后续独立任务；外部移动不当作归档命令。
- 原文件追溯／相似算法不在当前闭环实现，GIF／视频不参与画质判断。

## 6. 后续验收场景

这些是实现验收清单，本补充 PR 不实现功能测试。

| 场景 | 应得到的结果 |
|---|---|
| 新程序打开旧 v1～v4 库 | 在写入前明确拒绝；数据库与媒体不变；提示新目录建库、重新导入 |
| 新目录建库／已有路径 init | 新库基本读写正常；已有库或冲突文件不覆盖 |
| 新格式未来升级失败或版本过新 | 有版本保护与事务测试，不以“开发期旧库可丢”取消保护 |
| `123456789_p2.png` | Pixiv、ID、平台 p2 成为待核查建议；进收件箱，不自动确认／归档 |
| 多行 Pixiv／X／Zerochan 链接混一行坏链接 | 各有效行独立解析，仍一图一卡，无页码待核查 |
| 3 图追加 2 链接 | 明示范围确认后逐图追加，不按行分图，不传播至未选同组图 |
| 重复链接／清空输入 | 不重复来源，不覆盖已确认页码；清草稿不删已有来源 |
| Pixiv 完整确认，X 页码未知 | 可以正常归档；X 仍待核查 |
| 12 图中 3 图缺项 | 全批列缺项，由用户另选正常／强制范围，不自动分流 |
| 无来源强制归档 | 显式执行，仍无确认来源，不补造 p0／画师，不连带同组图 |
| G1=A＋B，G2=B＋C | 用户选择保留或合组，全库 B 一卡，组内位置分别显示 |
| B 有两组共享 tag | 任一组标签能找到 B；移出一组不抹掉另一组仍提供的 tag |
| B 的 Pixiv p1、X p0 | 分别记录；其他成员不因此继承 B 的来源 |
| 相同 hash 带新文件名再次导入 | 文件可复用，新线索保留、旧原名不覆盖，状态不重置 |
| 不同 hash 同 ID／页码，或表情差分 | 不自动覆盖／吞为版本，后续人工确认关系 |
| 已归档图补来源／改组标签 | 不自动退回收件箱，关系改动不搬文件；提示实际影响 |
| 转载账号发布／手贴来源链接 | 不认定为画师或本地文件获取证据 |
| 快速切图／筛选变动 | 旧请求不串图，进度／草稿按评审策略处理 |
| 新入库或归档复制中断、目标被占用 | 不覆盖／不丢图，有错误与恢复；不以放弃旧库作免责 |

## 7. 仍需明确的设计项（不是旧库映射）

- 具体新表、索引、约束、格式标识／版本边界与中性文件命名。
- 作者关联层级、合作创作与多组冲突；单图隐式组／组外操作；删除及误关联拆开的语义。
- 核查状态冲突、被驳回建议及规则依据留存；已确认／待核查来源筛选口径。
- 检查队列、上一张／下一张／跳过、草稿自动保存的位置与时效。
- 按选择顺序批填平台页码、退回收件箱的操作入口；全库多组／多来源标题和标志。
- 规则包试运行及稳定 API；版本人工关联／拆开、默认展示文件与缺失回退。

相关实现前明确，不把助手建议冒充用户已确认需求。旧状态、来源、日志映射和旧平台目录搬迁已取消，不再作为开工阻塞项。
