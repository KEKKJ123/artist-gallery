# 0009 开发期旧库不迁移，新模型使用新建图库

- 日期：2026-10-28
- 状态：采纳；在 T1 实现，本记录本身不改变运行行为。
- 部分取代：[ADR 0008](0008-以图片为中心的整理与来源模型.md) 中旧库兼容、记录映射和旧平台目录搬迁的实施安排。

## 背景

PR #16 合并后，红豆明确说明：项目仍处于开发状态，旧图库数据已有异地备份，可以舍弃旧开发库，由红豆自行手动删除文件，不需要开发旧数据迁移、状态或来源映射。

因此，继续保留 v1～v4 到新模型的升级桥、旧字段兼容投影和平台目录搬迁流程没有必要。复用现有代码不等于必须兼容旧数据库。

## 决定

1. T1 直接为新建图库建立新模型；不实现旧 v1～v4 库的数据迁移、字段／状态／来源映射、旧日志转换或旧平台目录搬迁工具。
2. 旧库及其文件由红豆手动处理。AI 不因本决定删除、清空、重建用户图库，也不访问备份作清理；程序不提供隐式“发现旧库就清空重建”的行为。
3. 新格式需要明确且可靠的格式标识／版本边界，不能把新库版本号重置后误认旧库。具体标识与 schema 在 T1 评审。
4. 新程序打开旧格式时，在任何迁移、内置平台同步或其他写操作前拒绝，明确提示“不支持旧开发库；请在新目录建库并重新导入”。拒绝后原数据库和媒体文件不变。`init` 遇到已有库或冲突文件不覆盖，不能把拒绝旧库变成原地重建入口。
5. T1 可以替换当前初始 schema，并移除仅服务旧格式的运行时迁移链和兼容业务；旧实现仍可通过 Git 历史追溯。读写、查询、CLI 和前端基础浏览须配套适配，不能靠保留旧字段假装已经切换。
6. **这是一次性的开发期格式边界，不是取消版本管理。** 新格式投入使用后的结构演进仍需版本检查和可验证的迁移；未知／过新／损坏库不得当作空库创建。
7. 新 schema、格式标识与版本管理代码开工前仍须与 sky 协调，避免同时修改。旧升级成功测试可替换为拒绝且不改动旧库的测试，文件安全、隔离、分层及交互回归仍保留。

## 理由与代价

- 去掉未经使用验证的旧模型兼容成本，直接验证新建库与新工作流程。
- 无需猜测旧自动归档、组来源和页码是否经过人工确认，也无需编造旧日志映射。
- 代价是旧图库不能直接用新程序打开；需要自行处理旧库，在新目录建库并从备份／原文件重新导入。重新导入是新流程的普通输入，不是恢复旧数据库关系。
- 用户有备份是本次决定的背景，不削弱今后对源文件删除、归档移动、备份一致性或不可逆操作的保护。

## 实施边界

本次补充 PR 只更新文档与开发约定，不改 schema、迁移代码、媒体文件或暂停分支。后续按 [transition.md](../transition.md) 实施；图／组／来源／版本模型及正常／强制归档规则维持不变。
