# 新整理模型：代码过渡与迁移验收

- 日期：2026-10-28
- 状态：路线切换计划；本文不执行迁移。需求以 [design.md](design.md) 为准，决定见 [ADR 0008](decisions/0008-以图片为中心的整理与来源模型.md)。
- 基线：main `0e3b8fc`；数据库 v4；后端 208、前端 222 项测试是已验证的旧模型基线，不是新路线完成度。

## 1. 分支、范围与交付规则

1. 沿用现有仓库与历史，不新建项目、不重写 main、不清空用户图库。
2. `feat/image-details-captions` 保持暂停，不合并、不改写或删除。本路线从 main 开始，不继承该分支的旧模型假设。
3. 本 T0 PR 只修改文档和开发约定，不动 Python／Vue／静态构建产物，不追加 MIGRATIONS，不创建或打开用户图库。
4. 后续从已合入的最新 main 分别开分支。main 仅经 PR 合入，由红豆审核并合并；同一阶段可拆多个完整、可验证的 PR，不维持长期“大重构分支”。
5. 阶段名是依赖顺序，不是必须一次改完的文件清单。每个 PR 要给出可运行范围、兼容边界与回退方式，不能先破坏读写流程再承诺下次修复。
6. 业务模型兼容与物理搬文件分离；数据库回滚不能自动撤销磁盘移动。不可用 Git 代码回滚代替图库备份。

## 2. 现有代码的去留

| 代码／能力 | 处理方向 | 注意事项 |
|---|---|---|
| `core/fileops.py` | 保留 | 复制、hash、校验与安全落位仍是底座 |
| `core/thumbnail.py`、`core/media.py` | 保留并适配文件版本 | 缓存仍面向具体文件内容；逻辑图片不应直接冒充 hash |
| `core/recognize.py`、`core/platforms.py` | 保留已有识别样本与防误识别规则，重定输出语义 | 从自动归档变为待审线索；页码未知不填 p0；规则包后续单独实现 |
| `core/importer.py` | 保留安全入库／确认后删源能力，替换业务编排 | 移除“平台决定目录和作品”“hash 重复就跳过所有信息” |
| `core/db.py`、`schema.sql` | 追加迁移，不重写历史 schema 或迁移 | 结构设计先评审，先与 sky 协调迁移版本 |
| `core/images.py` | 适配逻辑图片投影、版本及多来源 | 分页按图片身份，不因 join 多组／多来源产生重复卡片与错误计数 |
| `core/inbox.py` | 保留服务端筛选，替换收件箱判断 | 不再用 `work_id IS NULL` 或路径判断整理状态 |
| `core/browse.py`、文件夹 API | 旧库过渡兼容，之后退出主要业务入口 | 不再从平台文件夹推导来源或已归档；退役节点写在对应 PR |
| `server/` 应用工厂、请求连接、媒体响应 | 保留分层，业务接口按阶段适配 | 不共用跨线程连接，不削弱路径、Host 等边界 |
| 网格、选中、预览、zoom、快捷键、主题 | 保留 | 组件对新投影适配；一图一卡、稳定身份，不能被文件／组数量牵着变 |
| 分页、选择、导航等 composables 与 store | 保留模块边界 | 核查页新增请求同样防旧结果覆盖；不把所有业务重新塞回 inbox store |
| `NavPanel`、`Breadcrumb`、视图 URL | 调整为收件箱／已归档及关系浏览 | 旧书签处理需明示策略，不把平台目录等同于来源筛选 |
| 测试／CI | 保留安全与交互测试，替换已废弃的业务断言 | 不能为旧测试永久保留错误模型，也不能整批删测试冒充转向完成 |

## 3. T1：先评审关系结构，再迁移与适配读写

### 3.1 必须满足的结构能力（表名与字段待下一设计评审）

- 逻辑图片与具体文件版本分开；旧 image 的 id 和具体文件 hash 不能再承担所有身份语义。
- 图片与作品组是多对多；组内顺序属于成员关系，不放在图片唯一字段上。
- 平台帖子独立于作品组；图片与帖子可多对多，平台页码和人工核查信息属于对应关联。
- 内容 tag 继续组共享；搜索汇总有效关联并保留 tag 来自哪些组，不复制成无来历的图片标签。
- 整理状态明确持久化；至少一条完整确认来源才满足正常归档，强制归档是显式动作，不伪造核查结果。
- 来源线索保留输入依据及与确认结果的区别；保留原文件名、来源／获取证据，规则更新不覆盖人工结果。
- 画师与发帖账号不能默认等同；组／图作者关系的具体层级、合作署名与冲突处理不在本 T0 擅自定死。
- 相同 hash 可以复用文件，但仍接收新线索；不同 hash 的图片／版本关系保守处理，不自动用相似性合并。

### 3.2 旧记录如何映射：实施前的强制评审点

| v4 现有信息 | 必须保留 | 不能擅自推定 |
|---|---|---|
| `image` 的 rel_path、sha256、尺寸、原名、missing、added_at | 原值与可追溯映射；缺失记录也保留 | 不改路径、不丢文件、不凭相似性合并逻辑图片 |
| `image.work_id`、`image.page` | 旧组成员与顺序的原始信息 | 同一个 page 直接成为所有平台的已确认页码 |
| `source(work_id, platform, post_id)` | 全部平台、帖子信息与原组关系 | 旧组里每张图都已人工确认属于每条来源 |
| `source_hint` | 原始建议、缺项与原值 | 高置信、单图默认 p0 或已归档路径代表人工确认 |
| `artist/account/work_tag/tag/tag_alias` | 原有人工资料与关联 | 因为新 UI 未实现就可以清空这些表 |
| 原自动归档与旧目录 | 旧行为和记录的来历 | 把历史自动分拣写成用户已核查／主动强制归档 |
| `op_log` | 审计历史及映射依据 | 用旧 payload 直接撤销新结构；静默丢掉或伪造旧日志 |

**尚未决定、不得先写迁移的事项：**
- 旧自动归档图片在新状态中如何呈现：保留原显示位置并明确历史未核查，还是经用户选择回收件箱；默认策略须先确认。
- 旧来源到具体图片的映射：哪些证据可生成建议、哪些必须保持旧关系待核查；不能把组来源笛卡尔积变成人工确认。
- 新表／字段、索引、旧字段何时退役、来源页码冲突如何处理，以及不可解析旧日志的撤销边界。
- 画师编辑层级、单图使用共享 tag 的低负担入口，以及组／图片／文件关系的删除和误关联拆分策略。

### 3.3 迁移执行边界

1. 与 sky 确认无人同时追加冲突迁移；先审结构与映射清单，再编码。
2. 使用测试生成库验证；用户图库需要独立备份并在副本验证，不能把现有库默认为可丢弃测试数据。
3. 此阶段关系迁移不移动任何媒体文件；保留旧路径，通过映射支持继续显示。
4. 不只测新建库：覆盖 v4 库、旧组多来源、人工资料、missing 与升级失败；既有更早版本沿历史迁移正常升级。
5. 读／写入口成套适配。不能在新结构建立后，仍由旧 importer 写出不满足新约束的数据；临时适配必须写退役节点。
6. 审计与恢复可验证；迁移报告区分保留记录、待人工处理的歧义、不可恢复的信息。不可能从旧导入“已跳过”的重复文件里凭空恢复丢失线索。
7. 代码回滚不代表数据库能降级；提供与备份匹配的恢复说明，不让旧程序读新库强行改写。

## 4. T2：打通最小闭环

按可验证的小批次实现，必要时前后端同一 PR 配套交付：

1. 新文件安全进入收件箱；识别输出建议，不高置信直达归档；重复文件的新线索保留。
2. 收件箱／已归档按显式状态读写；保留整体计数与有无建议筛选，移除平台目录对状态的决定作用。
3. 检查页按单张前进，允许多选；多行链接逐行解析、只追加，已有来源明确解除；批量“每个链接 × 每张图片”先确认范围。
4. 来源 ID 与平台位置核查；缺位置留待核查；至少一条完整确认即可正常归档，不被额外未完成来源卡住。
5. 明确选中范围的正常／强制归档及对应撤销；混合缺项整批先报告，由用户另选，不部分执行。
6. 复用固定标题与文件大小，绑定当前逻辑图片的实际展示文件版本；不照搬暂停 PR 的旧多来源／页码假设。

上述流程的“保存下一张”不隐式归档；多来源／组编辑不自动改变整理状态。

## 5. T3／T4 与后续边界

- T3：多组归属编辑与组共享 tag 来历、画师手动绑定与多平台账号、按关系浏览搜索；校验主网格与总数按图片去重，组编辑展示全部影响范围。
- T4：平台规则包单独设计版本、命中次序、校验与官方／自定义兼容；画师规则另行规划，不引入通用脚本引擎。
- 目标两区的中性文件命名与搬库单独评审，不按平台分目录。旧平台目录仅用于过渡，不能作为长期隐性分类规则。
- 搬库前显示 A→B 清单与确认，建立中断恢复和逐文件校验；目录创建、文件落位、数据库更新、旧副本清理不能假设由一次 SQLite 事务同时回滚。
- T4 不是可以拖延所有新存储决策的理由：新写入路径在相关 PR 先确定；不继续为新数据引入平台绑定路径、再留给未来重复搬迁。
- 版本比较／原文件追溯只保留必要关系空间，算法不在当前闭环中实现；GIF／视频不参加画质判断。
- 旧文件夹 API、单组字段、兼容投影和旧写入器的退役随替代入口的 PR 明确完成，不永久维护两套生产业务。

## 6. 贯穿流程的验收场景

这些是后续测试和人工演练的验收清单，本 PR 不是它们的测试实现。

| 场景 | 应得到的结果 |
|---|---|
| 文件名为 `123456789_p2.png` | Pixiv、帖子 ID、平台 p2 自动成为待核查线索；图片进入收件箱，不自动确认／归档 |
| 粘贴 Pixiv、X、Zerochan 各一行链接 | 当前图片有多个来源线索，不增加卡片；无页码继续待核查，其他有效行不受坏行影响 |
| 多选 3 图、追加 2 链接 | 明示影响 3 图和 2 来源，用户确认后逐图追加；不按行分图，不给同组未选图片添加来源 |
| 输入重复／等价链接、删空输入框 | 来源不重复，已确认页码不被空值覆盖；清草稿不删除已有来源 |
| Pixiv 完整确认、X 页码未知 | 可以正常归档；X 仍待核查，不能被一并“确认” |
| 12 图有 3 图缺项 | 全批先列缺项，用户重新选择正常／强制范围；不执行前 9 张、暗中强制其余 3 张 |
| 无来源图片被选中强制归档 | 进入已归档但仍无确认来源；没有生成 p0、作者或链接；同组其他图片状态不变 |
| G1=A＋B，G2=B＋C | 用户可保留两组或明确合并；全库 B 仅一张卡片，两个组分别显示自己的位置 |
| B 继承两组 tag，其中一个 tag 重复 | 任一组 tag 都可找到 B；移出一组后仍保留另一组提供的标签与来历 |
| Pixiv p1 与 X p0 对应 B | 两个平台位置独立；给 B 加 X 来源不把 A／C 标为 X 发布 |
| 同 hash 再次导入但文件名新增来源 | 文件可复用，线索不丢、旧原名不覆盖、图片状态不被自动重置 |
| 不同 hash、同 ID／页码；表情差分 | 不覆盖旧文件、不自动吞成版本；能人工确认关系，差分仍独立 |
| 给已归档图补来源／改 tag | 不自动退回收件箱、不因关系变化搬文件；组修改显示实际影响 |
| 来源链接的发帖者是转载账号 | 不自动把账号认定为画师；发布关联与文件获取证据分开 |
| 快速切图、切筛选、批量后列表变动 | 旧请求不写新图；进度／草稿策略按评审结果实现，不串图、不漏项 |
| 迁移失败／复制中断／目标被占用 | 不删用户文件、不覆盖、不丢元信息，有恢复与明确错误 |

## 7. 建议与待定项：不能当作已确认功能直接实现

- 检查队列是否在开始时固定图片身份列表，以及上一张／下一张／跳过的细节。
- 草稿是否自动保存、保存到浏览器还是图库、保留时长；须区分草稿与正式来源，不能静默确认。
- 单图隐式单成员组、按选中顺序批填平台页码、回到收件箱等操作入口与交互。
- 全库多组／多来源标题显示优先级、已确认与待核查来源筛选口径、被驳回建议如何保留审计。
- 规则包试运行、预览与回退界面；包格式、安全限制与稳定 API 边界。
- 文件版本人工关联／拆开、默认展示版本切换，以及缺失展示文件时的回退。

这些不应阻止 T0 合并，但相关实现前必须明确；T1 的迁移映射待定项则直接阻止开始写迁移。

## 8. 各 PR 提交前的检查

- 范围与回退说明清楚；不夹带图库、图片、数据库、token、一次性浏览器脚本。
- pytest、ruff format --check、ruff check；前端 npm test，改前端必须构建并提交一致的 static。
- `.vue` import 大小写逐字匹配，文本 UTF-8 无 BOM、LF；相对路径仍跨设备可用。
- 功能变化更新 CHANGELOG，文件改动在回复中说明；数据库迁移 PR 需先协作确认版本。
- 交互变更用真实浏览器事件验证并检查截图；纯文档 PR 检查链接、前后口径和实际改动范围，不伪造功能验证。
