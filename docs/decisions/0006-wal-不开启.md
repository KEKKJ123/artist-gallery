# 0006 SQLite WAL：M1 不开启
- 日期：2026-10-27
- 状态：采纳

## 背景
M0 阶段已在 `db.connect()` 设置 `busy_timeout = 5000`，当时没有常驻进程，
WAL 不在考虑范围。M1 引入 Starlette server 后需要重新评估。

WAL 的好处：读写并发不互阻，导入时前端仍能加载缩略图。
WAL 的代价：程序运行时图库目录下会多出 `library.db-wal` 和 `library.db-shm`
两个临时文件；若进程被操作系统强杀（Android 后台驱逐是常见情形），
这两个文件留在磁盘，此时只复制 `library.db` 会丢失 WAL 中尚未 checkpoint
的改动，且不会有任何报错。

## 决定
**M1 不开启 WAL。**

理由：
1. 红豆的主要同步方式是"直接复制整个图库文件夹到手机"。WAL 给这个操作
   引入了静默数据丢失的风险，代价超过并发收益。
2. 当前规模（百至千张）下，5 秒 busy_timeout 已足够防止短暂写入冲突导致
   前端报错；实际卡顿可能性极低。
3. Android 端 App 被杀的概率远高于桌面程序，WAL 文件残留风险更大。

## 后续条件
若将来出现以下场景之一，再单独评估：
- 实际测量到 server 并发读写冲突导致 UI 报错；
- 同步方式改为 Syncthing / 网络同步（不再手动复制文件夹）；
- 多人在局域网共用同一个图库。

届时可在 server 启动时执行 `PRAGMA journal_mode=WAL` 并在导出命令中
执行 `PRAGMA wal_checkpoint(TRUNCATE)`，现有代码结构无需改动。
