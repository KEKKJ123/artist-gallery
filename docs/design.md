> v0.9：转向以图片为中心的整理流程。本文记录目标需求，**不代表代码已经实现**。代码转向与验收见 [transition.md](transition.md)，模型决定见 [ADR 0008](decisions/0008-以图片为中心的整理与来源模型.md)，旧库处理以 ADR 0009 为准。
> v0.7 及以前的方案保留在 Git 历史与历史 ADR 中，不再作为新业务开发依据。暂停分支 `feat/image-details-captions` 上的 v0.8 未合入 main，不视为现行实现。

## 1. 目标与范围

- 本地画师作品图库：**以图片展示，以作品组组织和共享内容 tag，以画师关联创作者，以平台发布记录保存来源，以文件版本容纳副本**。
- 起点是明日方舟角色红豆，之后通过 tag 命名空间扩展到其他角色与事物。
- 设计目标：1 万张图片以内可日常整理与浏览；不能依赖相似图或原图判断算法先完成。
- 用户通常导入不同图片，重复与相似版本是需要处理的少数情况，不把所有导入强制变为查重任务。
- 平台：Windows、Android（APK 为目标，Termux 为开发者路径），以及局域网访问。
- 手动整理是完整功能；下载器、联网取资料、相似算法都是可选增强。

## 2. 对象与关系（概念模型，不是 SQL）

| 对象 | 含义 | 关系与边界 |
|---|---|---|
| 图片 | 一幅具体画面，拥有稳定身份 | 主网格一图一卡；可关联多组、多来源、多个文件版本 |
| 文件版本 | 该画面的具体文件 | 保存相对路径、hash、尺寸等；压缩／缩放副本可以归为版本，不因文件数增加卡片 |
| 作品组 | 用户组织的一组图片 | 多对多成员关系；每组独立顺序及共享内容 tag；不是平台帖子 |
| 画师与账号 | 创作者及其各平台身份 | 一个画师可有多个账号、许多作品；发帖者不必是创作者 |
| 平台发布记录 | 具体平台上的帖子／作品页面 | 由平台与帖子 ID 定位；与图片关联，并记录对应的平台页码 |
| 内容 tag／别名 | 角色、系列等分类词 | 组共享；搜索图片时汇总其所属组的有效 tag，保留组来源 |
| 识别线索 | 文件名或链接提取的待审查信息 | 有依据但不等于人工确认；可先保存，再核查与补齐 |
| 整理状态 | 收件箱／已归档 | 图片自身的明确状态，独立于组、路径、来源核查状态 |

### 2.1 多组、多来源与页码

```text
作品组 G1（tag：夏日）         作品组 G2（tag：精选）
  A：组内 p0                   B：组内 p0
  B：组内 p1                   C：组内 p1

同一图片 B：全库一张卡片
  文件版本 B1、B2
  Pixiv 帖子 P：平台 p1
  X 帖子 X：平台 p0
```

- 同一画师在 Pixiv 发 A＋B、在 X 发 B＋C：用户可保留两组或合成一组，**程序不自动合并**。
- 图库组内页码与平台帖内页码分开；不知道平台位置时不能借用组内位置，也不能填成 p0。
- 平台帖子只包含某组的部分图片时，来源仅关联这些图片，不传播给整组。
- B 可按 G1、G2 的 tag 被找到；移出 G1 后，只解除 G1 提供的 tag。相同 tag 由 G2 继续提供时仍有效，不能物理复制标签后遗失来历。
- 表情、服装等内容差分是独立图片，不作为低画质文件吞掉；是否放进同组由用户组织。
- 画师归属的具体编辑层级、合作创作与组内冲突处理尚待设计，不能从发帖账号直接推断。

### 2.2 内容 tag 与来源标签

- 内容 tag 示例：`character:红豆`、`series:明日方舟`、`meta:R-18`；组共享。不带命名空间的可作为普通内容 tag。
- 来源可以显示为标签：`Pixiv:123456789`、`X:1849000000000000000`、`Zerochan:3017022`，并能按平台／ID 检索；**内部保存图片与发布记录的关联，不是一组共享的普通 tag**。
- 组页码、平台页码不是全局普通 tag；不能让组内每张图同时继承 p0、p1、p2。
- “图片在 X 发布过”与“本地这份文件从 X 获得”分别保存；手贴链接不制造获取记录或原图证明。

## 3. 整理状态与归档

| 图片情况 | 正常归档的来源条件 | 强制归档 |
|---|---|---|
| 无来源，或只知道平台 | 不满足 | 用户可自选图片明确执行 |
| 有具体帖子 ID，但未核查或平台页码未知 | 不满足，继续待核查 | 同上 |
| 至少一条来源的具体帖子与平台页码已人工确认 | 满足 | 无需为其他待核查线索强制归档 |
| Pixiv 已完整确认，X 尚待补页码 | 满足；X 仍待核查 | 不把 X 自动标为已确认 |

- **归档由用户执行**。文件名识别成功、来源核查保存、建立作品组均不等于自动归档。
- 正常归档至少需要一条完整人工确认的来源；不擅自增加“必须有画师／内容 tag”的门槛。单图帖也不能从无页码链接擅自推定 p0，需有核查依据。
- 强制归档只跳过信息完整性门槛，不跳过文件安全校验；不补造 ID、页码或画师，不确认未核查线索，不连带归档同组其他图片。
- 已归档不保证信息完整；之后可补资料，不因新增待核查来源自动退回收件箱。
- 批量选择混有缺项时：列出每张缺项，由用户重新明确正常／强制归档范围；不自动分流、不部分执行、不暗中强制归档。
- 归档写操作日志，对应撤销必须同批交付；确认与影响范围遵守 ADR 0007。多选添加来源的显式范围确认不能被“可撤销免弹框”取消。
- 来源核查状态是图片与发布记录关联的属性；归档状态是图片的属性。界面区分“没有已确认来源”和“还有待核查来源”。

## 4. 文件存放与安全

目标只分收件箱与已归档两区，不按平台／画师／组各存一份文件：

```text
图库根目录/
├─ library.db
├─ images/
│  ├─ _inbox/      收件箱文件
│  └─ archived/    已归档文件
└─ .cache/thumbs/  可重建缓存
```

- 上图表达目标布局；新写入的中性文件命名与必要目录分片在 T1 评审并配套实现，不能继续按平台写入、再推迟重排。旧开发文件不搬迁；具体路径协议仍未实现。
- 图片、组、平台发布和文件版本不以路径或文件名作为身份。改 tag、画师、组或来源，不应因此搬文件；原文件名独立保留。
- 数据库中的文件路径始终相对图库根目录、用 `/` 分隔；跨设备整体复制仍能识别。
- 归档状态以数据库明确记录为准，不再由 `work_id` 是否为空或目录推断。状态与两区文件移动须可恢复，不能把中断当作用户改变了状态。
- 导入只复制。图库内移动仍为“复制 → 校验 sha256 → 删除旧位置”；失败不覆盖、不丢文件。删除外部源文件须显式确认并再次校验（ADR 0005）。
- **旧开发库不迁移、不映射、不搬文件**（ADR 0009）。红豆已有异地备份并自行手动处理旧库；新模型直接新建图库、重新导入，不建旧路径兼容层。新程序应在任何写入前拒绝旧格式，不自动清空或原地重建；当前补充 PR 不操作图库。
- 取消的是旧库搬迁工具，不是新图库归档时的安全移动、日志与恢复；新格式使用后的版本升级仍需正常迁移与数据保护。
- 文件名不再足以重建全部多组、多来源关系，数据库备份更重要。结构化导出列入后续备份能力，格式与恢复流程未定。
- 保留外部改动后的扫描找回需求：按文件 hash 找回被挪动的具体文件版本，更新相对路径；找不到标为缺失，不自动删记录，不把外部移动当成归档／退回命令。作为文件版本与新存储适配后的独立任务交付。
- 保留明确选择范围的批量内容 tag、画师、组编辑与安全文件管理方向；旧“按平台模板重排全库”不再直接沿用，具体中性命名／重排／导出能力另审，不能把计划写成现有功能。

## 5. 导入、自动识别与检查页

### 5.1 自动分拣

```text
选择文件 → 安全复制／校验入库 → 收件箱
                                 ↓
                    平台规则生成来源、页码与分组建议
                                 ↓
                         用户检查、补充、纠正
```

- 自动化减少录入，不取代人工二次审查。高置信表示可更快核对，不是自动归档或自动确认。
- 保留已校准的 Pixiv `_pN`／`标题_ID`、X 下载文件名／media key、Zerochan 等识别能力；输出改为线索。不保留“命中平台→确定磁盘目录／完成归档”的行为。
- 规则只能生成有证据的信息。`123456789_p2` 可提取 Pixiv、帖子 ID、平台 p2；不据此推导画师、角色 tag 或另一平台链接。
- 无页码且无单图依据时保持未知。X 下载器的从 1 起编号可按规则转为平台 p0 起编号；各平台位置独立。
- hash 相同可复用已有文件存储，**仍解析新文件名等线索**；不覆盖旧原文件名、不丢新来源，不因文件去重自动合组。
- 不同字节的文件仅凭 ID／页码或相似性不能自动覆盖、合并版本。算法未落地时先分别保留，后续人工建立关系。
- 视频与 GIF 走同样的文件名识别和整理流程，不生成专用缩略图、不参加原图／画质判断；视频不读取宽高。
- 无法解析或损坏的文件报告失败并保留外部源文件；目录导入跳过各级隐藏目录，显式指定文件不受此限制。
- 更新规则可产生新建议，不能覆盖人工确认、自动合组、重排或重命名。

### 5.2 检查页输入

- 以**单张图片**连续检查，保存后去下一张；随时允许多选批量处理。保存核查结果与归档是独立动作。
- 展示预览、原文件名、自动识别内容与依据、已有来源、各来源页码及核查状态、组及组内位置。
- **多行文本框，一行一个链接**，解析 Pixiv／X／Zerochan 等平台与帖子 ID，不依赖平台 API 可用。
- 新输入只追加来源；已有来源单独列出，解除关联必须明确操作。清空输入框或删一行草稿不删除已有来源。
- 同一图片上相同平台＋帖子 ID 的重复链接去重，不覆盖已确认页码；同平台多个不同帖子可以并存。
- 某行无效只提示该行，不妨碍其他行解析。未知链接不当作已确认来源。
- 链接不含页码时只保存待核查信息，不能推定 p0，不能覆盖文件名已提取的对应页码；补齐并核对后才完整确认。
- 多选时含义是“全部有效链接添加给每一张所选图片”，**执行前明确确认范围**；不按行号分配、不传播到未选同组图片。批量追加不能自动确认各图的平台页码。
- 输入草稿、已保存待核查信息、正式确认来源三者不能混淆。草稿保存、连续队列等体验建议见实施计划的待评审项，不伪装为已确认需求。

## 6. 浏览、画师与内容 tag

- 主导航目标为收件箱、已归档；收件箱保留“全部／有来源建议／没有来源建议”服务端筛选及整体计数。
- 平台、画师、tag 与作品组成为可交叉检索的关系，不再互斥划分文件；搜索结果按逻辑图片去重，不因多组、多来源或版本数量重复卡片。
- 组内逐图显示 `p<n>`、支持查看同组图片。全库多组图片不能只标一个无上下文的 p0，具体展示样式待检查页草图评审。
- 组共享 tag 的编辑必须说明具体组和影响范围，不把“当前选择张数”等同于“实际受影响图片数”。多组修改目标不能隐式猜测。
- 单图如何在不增加用户负担的前提下使用组共享 tag、画师具体关联层级与冲突处理，实施前另审；不在本 PR 锁定表结构。
- 画师页展示多平台账号和图片；作品组详情展示成员与 tag；图片详情展示组归属、来源及文件版本。
- 原有内容 tag 补全、别名、最近使用与默认 tag 的需求保留，起始默认 tag 为 `character:红豆`；默认 tag 如何作用于新图的组、组外单图如何承接，随 T3 评审，不能为了实现默认值擅自强制合组。别名如 `Vigna`／`ヴィグナ` 的具体词条由用户录入或确认。
- 后续搜索保留命名空间与组合条件方向，例如 `character:红豆 -meta:R-18 artist:xxx platform:pixiv`；平台来源核查状态的筛选语义、语法与 UI 随搜索功能评审，不能把待核查来源悄悄当成已确认来源。
- 已归档图片可继续核查和补资料；“来源待核查”等可作为筛选能力，不引入第三种存放状态。
- 固定标题行、防止选中跳动、单选显示当前文件大小的需求继续保留，但暂停 PR 未实现到 main；按新模型选取复用，不整批合入旧来源查询与旧资料包方案。

## 7. 平台规则包（最小范围）

- 最小包只包含平台定义、作品／账号链接模板、文件名／链接识别规则，以及平台 ID、帖子 ID、平台页码等提取语义。
- 官方内置与自定义规则采用可共享的统一格式是目标；格式、版本兼容、优先级、冲突与安全校验仍需设计。
- 画师规则是另一项工程；画师资料库、tag 词库及别名集不强绑进最小平台包。
- 不实现“一切皆规则”，不执行资料包中的任意 Python／JS，不允许规则跳过审查、文件安全或撤销流程。
- 稳定第三方规则 API 是否开放、开放范围与时间未定，不因内部有 HTTP 接口就宣称已开放 API。

## 8. 技术架构、运行与备份

- 保留 Python 3.12+、SQLite、Pillow；Web 为 Starlette + uvicorn，前端 Vue 3 + Pinia + Vite。下载器 gallery-dl 是 M3 目标，尚未实现。
- 分层：`core/` 业务不依赖 Web；`server/` 解析请求并调用业务；前端组件、store、composables、纯函数各守职责，见 [modules.md](modules.md)。
- 运行时依赖须为纯 Python 或 Chaquopy 有可用包；Android APK 为 Briefcase／Chaquopy + WebView 目标，由 CI 构建（ADR 0003、0004）。
- 当前 CLI 仍是 `init`、`import`、`status`、`serve`；本轮文档不新增命令或接口协议，使用方式见 README。
- 所有资源本地打包，无 CDN；默认 localhost，局域网模式显式开启且无登录保护。
- 图库整体复制，`.cache/` 可排除；复制或备份须保证数据库与文件一致，稳妥方式是停止写操作／停服务后复制。不开 WAL 不等于可以在迁移、导入或搬文件时任意复制。
- 同时只在一端修改，双端合并、结构化导出与恢复流程后续实现；版本迁移与物理搬库须先备份、在副本验证。
- GPL-2.0-or-later；M1 全部完成后公开仓库的约定不变。

## 9. 实施路线与现状

**已完成的是旧模型下的 M0、M1a、M1b、预览缩放／触摸和模块化重构，不代表新模型已交付。** 目标不是重开项目，而是保留基础能力、逐批替换旧业务假设。

| 阶段 | 交付范围 | 验收重点 |
|---|---|---|
| T0（PR #16 已合并） | 设计、ADR 0008、开发约定与过渡计划；本次以 ADR 0009 补充旧库决定 | 均仅文档；运行代码与图库不变 |
| T1 | 新建图库模型、格式边界与配套读写 | 旧格式写入前拒绝且不改原库；新建库流程可用；不做旧库映射 |
| T2 | 新导入／收件箱／检查／归档闭环 | 建议、逐图核查、多行追加、页码、正常与强制归档、撤销 |
| T3 | 多组共享 tag、画师及关系浏览编辑 | 多组搜索去重、标签来历与影响范围、可纠错 |
| T4 | 最小平台规则包 | 格式／校验／更新单独评审；中性新存储随 T1／T2 交付，无旧库搬迁 |
| 后续 M2 | 更完整的搜索、画师／组／图片浏览 | 按真实整理流程扩展 |
| 后续 M3／M4 | 下载器／Android APK | 作为输入增强与外壳，不改变同一套整理规则 |
| 后续 M5 | 相似候选、原文件追溯、浏览器脚本、双端合并 | 不阻塞基础整理，不自动删除差分 |

T0～T4 是原 M1c～M1e 的替代实施次序，不是已实现功能或不可拆分的大 PR。T1 不再以旧状态／来源映射为开工前提；具体新 schema、格式识别及业务待定项仍需设计。代码去留与验收见 [transition.md](transition.md)。

## 10. 原文件追溯与版本比较（未排期）

- 主要目标：找到**最接近画师发布原文件的版本**，不是“文件最大／像素最多／PNG 优先”的排行榜。
- 完全相同的字节、同一画面的不同编码、内容差分、原文件证据分别处理。平台帖子 ID＋页码不是跨平台图片身份，也不是无条件覆盖证据。
- 原图／压缩版可以归入图片的文件版本；表情、服装、文字等差分保留为独立图片。识别未实现时先保留，人工决定；不让算法成为导入前置条件。
- 相似算法路线：哈希等粗筛 → 候选内容比对 → 人工确认关系 → 结合来源证据比较版本；阈值需真实插画校准，允许“证据不足”。
- 研究 pHash／dHash／颜色与网格差异等方法，不将小差异误当压缩噪声。JPEG 量化表、像素、格式、大小、ICC 等只是辅助信号，不能单独证明原图或压缩历史。
- 版本来源、获取依据、人工判断与未知分别表达；平台提供的最高尺寸也未必是上传前原文件。不能为手贴发布链接伪造文件获取证据。
- 首期不自动替换／删除；版本人工关联、默认展示版本、误关联拆开需先设计。未来如需移入回收区，必须另行实现确认、日志和恢复，不沿用旧“保留更优画质默认开”的规则。
- GIF／视频不参与此判断。算法附件仅是参考，未作为实现文件导入仓库；其中同 `(work,page)` 直接选优、GIF 首帧参与等前提不采纳。
