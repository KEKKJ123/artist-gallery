# 0010 图片直接关联属性，保留原名并支持增量导入

- 日期：2026-10-28
- 状态：采纳；T1 交付新结构和基本读写，核查／归档编辑留在 T2。
- 部分取代 ADR 0008 的作品组共享 tag、组页码及页码必填规则；ADR 0009 的旧库不迁移边界保留。

## 背景

详细模型评审后，红豆明确指出初版需要的是图片的 Pixiv／X 等发布 ID、各自 pn、画师和发布时间，以及画师的各平台账号；补充保留 `character:红豆` 等内容分类。为这些属性先建组、处理标签继承会增加无用操作。

红豆认可：图片直接关联内容 tag、画师与多个平台来源；pn 附属于对应来源且可未知；正常归档不必强迫填页码。存储尽量保留原文件名，外部源目录再次选择时增量导入，按文件 hash 保持已有整理结果。开发第一目标是减少用户繁琐操作，即使增加代码工作量。

## 决定

1. 不建立作品组、隐式单图组、组成员、组 tag 继承或通用规则引擎。`image_tag` 直接连接图片与内容 tag，图片直接关联画师。批量加属性作用于所选图片，不影响未选图。
2. 来源与内容 tag 分开：平台＋发布 ID 作为来源标签展示，内部有帖子和图片关联。`page` 是对应来源的可选位置，不是总页数、图片 ID 或独立 tag；发布时间属于平台发布，可为空。
3. 至少一条人工确认的具体平台发布满足正常归档来源门槛，页码／时间未知不阻断；缺来源可显式强制归档。自动解析不等于人工确认，保存核查不自动归档。
4. 文件以原名保存：合法且不冲突时保留，包括扩展名大小写；重名追加后缀，非法／过长名称必要清理，完整原名另存。文件路径不包含强制平台分类，目标两区为 `images/_inbox/` 与 `images/archived/`。
5. 逻辑图片与文件版本分开，内部用稳定记录 ID；SHA-256 判断字节相同。不同字节先独立保留，不自动判同画面或选优。
6. 增量导入是再次选择**外部源目录**，不是镜像同步：已有文件复用，状态、画师、内容 tag、人工来源不变；改名输入保留新名称和线索，重复建议去重。新增不同文件进收件箱；源目录减少不联动删图库。
7. hash 命中仍校验图库副本；副本缺失／损坏报错、不覆盖、不将重复输入列为可删源文件。修复能力后续单独设计。
8. 来源关联统一保存待核查／已确认／已驳回状态，独立证据保留原文件名／规则依据；规则或新输入不覆盖人工值。单纯平台线索（X media key）可没有帖子关联。
9. 旧 v1～v4 明确拒绝且不写入。新格式用 SQLite application_id=`0x41475259`、user_version 从 5 起，旧程序见过新版本也会拒绝。新格式后续正常追加迁移，不重复丢库。

## T1 实现边界

- `image`：稳定 ID、整理状态、画师外键、入库时间。
- `image_file`：所属图、原名、相对路径、hash、尺寸、缺失和展示标志；每图最多一个展示文件，导入事务成对创建。
- `artist/account`、`tag/image_tag`：直接属性关系，T1 只建立结构、投影与约束，后续提供编辑。
- `post/image_source`：平台发布、可空时间，以及图片对应的可空页码／核查状态；同图同帖一条关联，初版不表示同帖同图重复出现多个位置。
- `source_evidence/import_record`：按输入／规则去重证据，每次正式导入有记录；首次名称不被后续别名覆盖。导入路径不默认存入分类资料。
- 新 API：`/api/navigation`、`/api/archived`，保留 `/api/inbox?filter=`、`/api/platforms`、原图与缩略图。
- 删除旧文件夹 API／面包屑，旧 `?folder=` 提示已移除后回收件箱，不冒充来源筛选。
- 固定一行标题随基础浏览适配；文件大小、检查页、多行链接、来源确认、正常／强制归档及撤销、属性编辑不在本次假装交付。

## 理由与代价

原名保留资源管理器浏览能力，分类由内部身份关联，用户不必理解分组。程序承担去重、证据保留、批量查询与安全校验，用户不重复整理。不同编码／元数据变化会改变 hash，因此增量不能冒充视觉同图识别；物理文件名也不能恢复全部关系，仍需数据库备份。
